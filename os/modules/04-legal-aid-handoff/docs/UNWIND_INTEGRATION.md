# UNWIND Integration — Audit & Unwind Readiness

This project's `AuditEvent` table is append-only by convention (the API
never updates or deletes a row — see `backend/audit.py::log_event`, which
only ever inserts). This document describes the shape UNWIND (or any
external audit/replay system) can rely on.

## Event shape

```json
{
  "id": "audit_<hex>",
  "case_id": "case_<hex>",
  "actor": "system | citizen | <role>",
  "role": "CITIZEN | PARALEGAL | LEGAL_AID_WORKER | ADVOCATE | ADMINISTRATOR | REVIEWER | null",
  "event": "string, e.g. handoff_generated",
  "result": "ok | <custom>",
  "correlation_id": "string — groups related events across a single operation",
  "source": "backend",
  "details": {"...": "event-specific payload, e.g. {\"handoff_id\": ..., \"version\": 1}"},
  "created_at": "ISO 8601 timestamp"
}
```

## Events currently emitted

`case_created`, `intake_submitted`, `document_uploaded`,
`conflicts_recomputed`, `handoff_generated`, `handoff_reviewed`,
`handoff_approval_decision`, `handoff_transferred`,
`handoff_acknowledged`, `clarification_requested`,
`clarification_resolved_new_version`, `simulation_run`, `crash_test_run`,
`demo_seed`.

## Reading the trail

`GET /api/cases/{id}/audit` returns the full, time-ordered event list for
a case. Because every state transition in the handoff lifecycle
(generate → review → approve → transfer → acknowledge/clarify → new
version → verify) writes exactly one event, an external system can
reconstruct the full lifecycle of any handoff from this endpoint alone,
without needing direct database access.

## Unwind semantics

"Unwind-ready" here means: an external system replaying this event log
should be able to reconstruct case state at any point in time, because
(a) `HandoffVersion` rows are immutable snapshots (see
`docs/DOMAIN_MODEL.md`), and (b) nothing is hard-deleted — `Conflict` rows
generated by `recompute_conflicts` are cleared and regenerated only for
*unresolved* conflicts, and no other table is ever bulk-deleted by the
API. Actually reversing a specific action (e.g. un-approving a handoff)
is **not implemented** as a dedicated endpoint in this build — an external
UNWIND system would currently need to reason from the audit log and apply
compensating writes itself. Tracked in `docs/LIMITATIONS.md`.

## Agent traceability

Every LLM-backed agent call also writes an `AgentRun` row
(`GET /api/cases/{id}/agent-runs`) recording the agent name, provider
(`MOCK` in demo mode), and latency — so an audit/replay system can
distinguish deterministic engine output from agent-narrated output.
